# Build Prompt v2: Ontology-Driven Live Narration Engine (Cricket First)

Two parts. Part 1 goes into your project's `CLAUDE.md` (or system instructions) — it governs every session. Part 2 is the kickoff prompt you paste to start the build.

---

## PART 1 — Project Instructions (CLAUDE.md)

You are building a **domain-agnostic live narration engine**. Cricket is the first domain binding, not the product. The product is: any structured event stream + domain ontology → expert, real-time narration (text + voice).

### Non-negotiable architecture principles
1. **Core is domain-blind.** Nothing in `core/` may reference cricket concepts. Enforced by a CI grep test: words like wicket, batter, over, innings must never appear in `core/`. Core reasons only over upper-ontology classes.
2. **Domains are data, not code.** A new domain = new YAML files (ontology, rules, templates, persona) + a feed adapter. If porting to a new sport requires editing core code, the design has failed.
3. **Every decision must be explainable.** Significance scores carry a trace: which rules fired, each contribution, final score. No black-box scoring.
4. **Never state an ungrounded fact.** Generated narration may only contain claims entailed by the live state or the knowledge graph. Wrong facts are worse than no narration.
5. **Prototype pragmatism.** Lightweight typed YAML taxonomy + rules engine + property graph. No OWL, no RDF reasoners, no semantic-web frameworks.

### Repo layout
```
core/            # domain-blind: state engine, rules engine, significance scorer,
                 # narrative memory, tiered generator, grounding checker, TTS
ontology/upper.yaml        # abstract concepts shared by all domains
domains/cricket/           # ontology.yaml, rules.yaml, templates.yaml,
                           # persona.md, context/ (KG data), adapter.py
apps/video_ingest/         # score-bug reader (video → events)
apps/player/               # synced playback web page
tests/
```

### Upper ontology (starting set — `ontology/upper.yaml`)
Abstract classes the core understands:
- `Event` (atomic occurrence), `Actor` (participant), `Contest` (the match/session), `Phase` (labeled segment of a contest)
- `ScoringEvent`, `SetbackEvent` (adverse to one side), `RoutineEvent`
- `Milestone` (crossing a celebrated threshold), `ThresholdCrossing` (any metric crossing a defined line)
- `Streak` (run of similar events), `Pressure` (accumulating adverse events without relief), `Momentum` (directional trend in rolling metrics), `Reversal` (sharp momentum flip)
- `Storyline` (multi-event narrative thread with a state: building / peaking / resolved)
Each class defines the properties core expects (e.g., `SetbackEvent.severity`, `Streak.length`, `Momentum.direction`). Domain ontologies subclass these and bind domain events to them.

## PART 2 — Kickoff Prompt

### Mission
Build the prototype end-to-end: input is a **video file of an old cricket match**; output is **text commentary + spoken commentary (TTS)** synced to the video, generated by the ontology-driven core described in the project instructions.

### Pipeline
**A. Video → events** (`apps/video_ingest/`): ffmpeg samples frames every ~2s → vision LLM reads the on-screen score bug (calibrate crop region with me on 3 sample frames) → strict JSON readings → diff consecutive readings to derive ball-by-ball events → reject impossible transitions (score decreasing, overs jumping), interpolate gaps (replays/ads hide the bug). Cache all vision results to disk by timestamp.

**B. Domain adapter** (`domains/cricket/adapter.py`): maps derived ball events to ontology-typed events. Example: a wicket becomes `SetbackEvent` (against batting side) and, when it ends a 50+ stand, also emits a `Storyline` resolution. A dot-ball run becomes a `Streak` feeding `Pressure`.

**C. Core engine** (`core/`), per event:
1. **State engine**: updates generic metrics registered by the domain (score, rates, per-actor tallies, phase) — metrics are declared in domain YAML, computed by core.
2. **Pattern detectors**: generic detectors for `Streak`, `Pressure`, `Momentum` (rolling-window comparisons), `Reversal`, `ThresholdCrossing` — parameterized by domain config (window sizes, thresholds), implemented once in core.
3. **Rules engine + significance scorer**: rules in `domains/cricket/rules.yaml` reference ontology classes and state predicates, never raw code. Format:
   ```yaml
   - id: setback_under_pressure
     when: {event: SetbackEvent, context: {pressure: ">0.6", phase: endgame}}
     score: +35
     pull_context: [actor.dismissal_patterns, matchup.head_to_head]
   ```
   Core evaluates rules, sums contributions, clamps 0–100, and logs a full trace (rule ids + contributions). `pull_context` declares which knowledge-graph queries feed the prompt.
4. **Knowledge graph**: static context (player bios/form, venue notes, head-to-head, stakes) as a property graph — networkx or SQLite triples (`subject, relation, object, source`). I will supply `domains/cricket/context/` data for the test match; build a loader + query helpers (`neighbors`, `path`, `facts_about`). No invented facts.
5. **Narrative memory**: rolling buffer of recent lines + `Storyline` tracker (2–4 active threads with states). High-tier prompts must weave in an active storyline when relevant.
6. **Tiered generation** by significance: <25 → templates from `templates.yaml` (no repeat within 2 overs); 25–60 → fast LLM (Haiku), compact prompt; >60 → full LLM (Sonnet) with event, state, KG facts from `pull_context`, storylines, recent lines. Persona from `persona.md` — consistent, no real-commentator imitation.
7. **Grounding checker**: extract factual claims (numbers AND relational claims like "his third fifty") → verify against state/KG → regenerate once with correction on failure → template fallback. Log every rejection.

**D. TTS + playback** (`apps/player/`): TTS per line (edge-tts to start), 3 excitement levels mapped from significance to rate/pitch. Single-page player: video + text feed appearing at each event's `video_ts` + audio synced, never overlapping clips (skip/duck lower-priority audio). Offline-first: pipeline emits `commentary_track.json` + audio files; the page replays them.

### Milestones (show me each before proceeding)
1. **M0 — Core proof, no video**: upper ontology, rules engine, pattern detectors working on a synthetic event file; unit tests; show me score traces for 20 synthetic events.
2. **M1** — Score-bug reader on my video: 10 consecutive JSON readings.
3. **M2** — Full first innings as ontology-typed events; I validate against the real scorecard.
4. **M3** — State + significance with rule traces for one innings.
5. **M4** — Tiered text generation with memory + grounding; show a 5-over stretch including a wicket.
6. **M5** — TTS + synced playback page.
7. **M6 — Portability proof**: narrate a small *non-cricket* synthetic stream (e.g., a football half or a mock patient-vitals feed) by adding only a new `domains/<x>/` folder — zero core changes. This is the acceptance test for the whole architecture.

### Success criteria
- `core/` contains zero cricket vocabulary (grep test passes).
- Event extraction ≥90% accurate vs the real scorecard.
- Zero ungrounded facts survive to output.
- Every significance score reproducible from its logged rule trace.
- M6 domain added with YAML + adapter only.
- Full T20 innings processed for a few dollars of API spend (report actuals).

### Tech
Python 3.11+, ffmpeg, Claude API (vision + generation), edge-tts, networkx or SQLite, plain HTML/JS player, pytest. No heavy frameworks.
